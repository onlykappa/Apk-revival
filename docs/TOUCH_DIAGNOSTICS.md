# Meego touchscreen/zoom investigation — 2026-10-13

## Current outcome

The user reports slow/stuttering Meego zoom gestures. The cause is **unresolved**. No touch latency, tap-loss rate, drag accuracy or zoom FPS was measured. ## Capture through APK Revival

With Android running, choose **Setup > Capture input diagnostics**. Select one comparison label, return to Android when the countdown appears, and repeat the same gestures for ten seconds. Reports are stored in `~/.local/share/apk-revival/input-diagnostics/`.

Capture Meego touchscreen and mouse/trackpad trials, then equivalent touch and mouse trials on a basic Android screen. Keep the mode, window size and game scene the same between touch/mouse trials. Use pinch-in/out, repeated taps, slow dragging and screen-edge targets. Repeat at the relevant fullscreen/window sizes and after launching from a stopped runtime. Record which gestures miss, how many attempts succeed, and whether the basic Android screen behaves differently. Opening a different basic Android screen remains a user action; this collector does not launch or force-stop apps.

The collector reads current Android window focus, input state/devices, size/density, existing properties, actual session-reported Wayland socket, compositor outputs and selected native SurfaceFlinger layer buffers. It does not guess output names, start/reset Android, install a game, reset frame statistics, change properties, map touch devices or alter saves. If Android is inaccessible it records host-only evidence and errors rather than using a stale saved IP. ADB success with missing Android services is recorded as a service failure; a ten-second gesture trial is skipped in that state, with graphics crash logs retained.

The report contains HWUI frame differences where Android supplies them, named explicitly as IntendedVsync-to-FrameCompleted durations. These are rendering statistics, **not physical touchscreen latency**. Native OpenGL/SurfaceView gameplay may be absent from HWUI data; zero samples mean unknown, not fast rendering. Raw SurfaceFlinger data for up to four actually reported matching game layers is retained separately. Its recent-buffer ring does not necessarily cover the whole ten-second trial. `dumpsys` snapshots have observer overhead and no physical contact timestamp. See [Android rendering profiling documentation](https://developer.android.com/topic/performance/rendering/profile-gpu).

An end-to-end input-to-photon latency comparison requires physical-contact and visible-response timing, such as synchronized high-speed video, or appropriately traced host/Android clocks. This build does not invent such a number from ADB command duration or subjective responsiveness.
